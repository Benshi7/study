Qué problema resuelve una base de datos

Antes de modelar nada, hay que poder responder para qué existe esto. Y la respuesta no es "para guardar datos" — para eso alcanza un archivo.

01De dato a información

La distinción que se evalúa

Un dato es un hecho registrado. La información son datos organizados de una forma que sirve para tomar decisiones. El salto no lo da el volumen: lo da el contexto. Y ese contexto es exactamente lo que una base de datos guarda junto con los datos.

02Qué es una base de datos, en serio

Elmasri arranca con una definición deliberadamente amplia:

"Una base de datos es una colección de datos relacionados. Con la palabra datos nos referimos a los hechos conocidos que se pueden grabar y que tienen un significado implícito."

Tan amplia que, como él mismo admite, el texto de esta página calificaría. Por eso agrega tres propiedades que sí acotan el término. Estas tres son las que conviene tener de memoria:

  1. Representa un minimundo. Un recorte del mundo real — también llamado universo de discurso. Y lo persigue: si cambia el minimundo, cambia la base.
  2. Es lógicamente coherente. Tiene un significado inherente. Un surtido aleatorio de datos no es una base de datos.
  3. Tiene propósito y público. Se diseña y se llena para algo, con un grupo de usuarios previsto.

Fijate lo que sale de ahí: una base de datos no es un depósito. Es un modelo de una porción de la realidad, que se compromete a mantenerse fiel a ella. Todo lo demás de la materia — el DER, la normalización, la integridad, las transacciones — existe para sostener esa promesa.

03Contra qué se inventó: el procesamiento de archivos

Para entender qué gana una base de datos, mirá el mundo anterior. Elmasri usa este ejemplo, y es el que mejor lo muestra:

En una universidad, la oficina de calificaciones mantiene su archivo de estudiantes y sus notas, con sus propios programas. La oficina de contabilidad mantiene otro archivo de estudiantes, con sus cuotas y pagos, con otros programas. Ambas oficinas necesitan datos del estudiante. Ninguna usa el archivo de la otra.

Ese arreglo tiene tres heridas, y las tres tienen nombre:

ProblemaQué pasa concretamente
Redundancia El nombre y la dirección del estudiante están guardados dos veces. Se derrocha espacio, y se duplica el trabajo de mantenerlos al día.
Inconsistencia El estudiante se muda y avisa en una sola oficina. Ahora hay dos verdades distintas sobre la misma persona, y el sistema no tiene forma de saber cuál vale.
Dependencia programa–datos La estructura del archivo está incrustada en cada programa. Si agregás un campo, hay que tocar todos los programas que abren ese archivo.

Hay un cuarto problema, más silencioso: cada aplicación bautiza los datos como quiere. Lo que en un archivo es nom_alu, en el otro es NombreEstudiante. En la metodología de bases de datos, en cambio, se mantiene un único almacén, definido una sola vez, y los nombres se definen una vez y los usan todas las consultas, transacciones y aplicaciones.

Ojo con esta confusión

Redundancia e inconsistencia no son lo mismo. La redundancia es el dato repetido — molesta, pero por sí sola no rompe nada. La inconsistencia es lo que pasa cuando una de las copias se actualiza y la otra no. La redundancia es la causa; la inconsistencia es el daño. Ese par vuelve en la Unidad 3, cuando normalicemos.

05Aplicalo al TP

El TP1 arranca así: "Usted ha sido contratado con el motivo de diseñar una base de datos para una cadena de farmacias." Antes de dibujar una sola entidad, respondé las tres propiedades para ese caso. Pensalo y después abrí.

Ver cómo se responden las tres
  • Minimundo: la operación de una cadena de farmacias — sucursales en distintas ciudades, su personal, y el stock de medicamentos. Todo lo que quede afuera de ese recorte no se modela, por más real que sea. Las ventas, los clientes y los proveedores existen en el mundo, pero no están en el enunciado: no van al modelo.
  • Coherencia: las entidades tienen que colgar unas de otras con sentido. Farmacia, Ciudad, Empleado, Medicamento forman un todo; una entidad suelta que no se relaciona con nada es señal de que la leíste mal.
  • Propósito y público: el enunciado te lo dice explícitamente al final, y es la parte que más gente saltea. Lista cuatro consultas que el modelo debe poder responder — cantidad de farmacias por ciudad, empleados según código postal, stock por laboratorio y stock por presentación. Ese es el criterio de aceptación. Si tu modelo no puede responder esas cuatro, está mal, aunque el diagrama sea impecable.
