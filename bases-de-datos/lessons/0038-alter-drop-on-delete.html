Cambiar la estructura, y qué pasa al borrar un padre

ALTER modifica una tabla que ya existe; DROP la elimina. Y ON DELETE decide qué les pasa a los hijos cuando se borra el registro del que dependen.

01ALTER TABLE

"Se pueden agregar/quitar/modificar campos a una tabla, modificar el tipo de un campo, agregar/quitar índices, agregar o eliminar restricciones." Los ejemplos del deck:

ALTER TABLE Curso ADD comentario CHAR(40) NOT NULL;
ALTER TABLE Curso DROP duracion;
ALTER TABLE Curso ADD CONSTRAINT ck_cod_empresa CHECK (codigo_empresa > 1);
ALTER TABLE Curso DROP CONSTRAINT fk_curso_requisito;
ALTER TABLE Curso ADD CONSTRAINT fk_curso_requisito
      FOREIGN KEY (codigo_curso_requisito) REFERENCES Curso (codigo_curso);

La última línea es una FK de Curso a sí misma: un curso que es requisito de otro. Es la misma relación unaria que Cod_Jefe en PROFESIONAL.

Para la hoja, la sintaxis del deck; en SQLite, menos

SQLite sólo acepta ADD, DROP COLUMN y RENAME: no deja agregar ni quitar restricciones con ALTER. Además, una columna nueva NOT NULL necesita un DEFAULT, porque las filas que ya existen tienen que tener algún valor. En el parcial escribí la forma del deck.

02DROP TABLE, y el orden

DROP TABLE Curso elimina la tabla con su estructura y sus datos. DELETE FROM Curso borra las filas y deja la tabla vacía. Son cosas distintas: una es DDL y la otra es DML.

Primero los hijos, después los padres

Si la integridad referencial está activa, no se puede tirar una tabla padre mientras haya hijos que la referencian. El script del TP5 tiene que borrar en el orden inverso al de creación. El orden de creación es padres primero; el de borrado, hijos primero.

03ON DELETE: CASCADE o SET NULL

"Cuando se intenta eliminar un registro de una tabla Padre que participa en una clave foránea, el motor de base datos validará que no exista ningún registro dependiente." Si existe, por defecto el borrado falla. El modificador de la FK cambia eso:

OpciónAcción, según el deckCuándo tiene sentido
CASCADEElimina automáticamente los registros dependientes de la tabla hija.El hijo no existe sin el padre: los teléfonos de un paciente, las consultas de su historia clínica (entidad débil).
SET NULLPone en NULL los campos de los registros dependientes.El hijo sobrevive sin el padre: si se va el jefe, el profesional queda sin jefe.
